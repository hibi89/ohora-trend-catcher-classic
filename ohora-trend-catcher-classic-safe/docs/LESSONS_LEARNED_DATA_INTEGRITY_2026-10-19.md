# OHORA Trend Catcher RAW v2.1 — 데이터 설계·개발 과정 반성 및 재발 방지

작성일: 2026-10-19  
대상: OHORA Trend Catcher 수집 파이프라인  
목적: 동일한 설계·검증 실패를 반복하지 않도록 원인, 책임, 검증 기준을 기록한다.

## 1. 핵심 반성

**수집 성공과 데이터의 신뢰성을 혼동했다.**

초기에 데이터 계약과 무결성 불변식을 확정하기 전에 API 수집을 시작했다. 이후 수집 속도와 배치 처리에 집중하면서 요청 식별, 관측 이력, 수집 커서, 완료 판정, 장애 복구 같은 기반 문제를 뒤늦게 발견했다.

진행 순서는 사실상 **수집 성공 → 속도 최적화 → 배치 확장 → 결함 발견 → 데이터 설계 보강**이었다. 올바른 순서는 **데이터 계약 확정 → 실패 시나리오 검증 → 최소 실수집 → 무결성 검사 → 확장**이어야 했다.

이 문제는 사용자의 요구가 부족해서가 아니라, 구현을 담당한 AI가 설계·검증 단계에서 선제적으로 확인해야 할 위험을 충분히 검토하지 못한 데 있다.

## 2. 무엇을 잘못했는가

### 2.1 요청 ID와 관측 이력

- 실행 간 `request_id` 충돌 가능성을 사전에 차단하지 못했다.
- 동일 게시물을 여러 날 조회할 때 좋아요·댓글·팔로워의 **관측 시점별 기록**이 독립적으로 남는지 먼저 검증하지 않았다.
- 요청 로그, 게시물 관측, 실행 정보의 일대일·일대다 관계를 실제 재실행 테스트로 검증했어야 했다.
- **주의:** 코드의 충돌 가능성이 확인됐다는 사실과 기존 로컬 DB에서 실제 데이터가 손상됐다는 주장은 다르다. 손상 여부는 별도 진단 전까지 미확정이다.

### 2.2 최신화·과거 수집·누락 구간의 상태 관리

- `front`, `history`, `catchup` 각각의 커서와 상태 전이를 처음부터 명확하게 모델링하지 못했다.
- 수집 중단, 새 게시물 유입, 누락 구간 발생, 중복 실행, 날짜 경계 변경 상황을 먼저 시뮬레이션하지 않았다.
- 조회 성공이 곧 연속적인 과거 게시물 확보를 의미하지 않는다는 점을 완료 판정에 충분히 반영하지 못했다.

### 2.3 1년치 완료 판정

- 오래된 게시물이 관측됐다는 사실만으로 `backfill_done`을 확정할 위험이 있었다.
- **최신 페이지에서 오래된 게시물 발견**과 **과거 커서를 연속적으로 따라가 기준일에 도달**하는 것은 전혀 다른 증거다.
- 완료 판정은 페이지별 커서·시간 범위·종료 근거를 남긴 뒤 내려야 했다.
- 기존 `backfill_done=1` 기록도 독립 증거가 없으면 검증 완료로 취급해서는 안 된다.

### 2.4 캐러셀 및 부분 데이터

- 부모 게시물만 저장됐거나 자식 미디어가 누락된 경우에도 완전한 수집으로 오인할 수 있었다.
- 데이터 필드별 `complete`, `partial`, `unsupported`, `unknown`의 의미를 선제적으로 정의했어야 했다.
- 같은 게시물을 재관측할 때 빠진 미디어를 보완할 수 있어야 한다.

### 2.5 API 응답 식별·저장·복구

- Business Discovery 응답이 요청한 계정에 속하는지 검증해야 했다.
- 외부 API 호출 전 요청 계획 기록, 응답 원본 보관, DB 트랜잭션, 중단 후 재개를 하나의 장애 시나리오로 설계했어야 했다.
- 전송 여부가 불확실한 배치를 자동 재호출하면 중복 수집과 예산 낭비가 생길 수 있다.
- 저장 실패와 API 실패를 혼동하지 말아야 하며, 원본 응답이 있으면 네트워크 재호출 없이 복구하는 방식을 우선해야 한다.

### 2.6 테스트 통과의 과대해석

- 오프라인 단위 테스트 통과는 합성 데이터와 구현 경로의 일부 검증일 뿐이다.
- **기존 로컬 SQLite의 정합성, 실제 Meta 응답의 다양성, 294계정 운영 안정성, 1년치 데이터 완결성**을 입증하지 않는다.
- 앞으로 보고할 때 **구현 완료 / 오프라인 테스트 통과 / Windows 로컬 DB 검증 / 제한적 실수집 검증 / 운영 승인**을 반드시 분리한다.

## 3. 실제로 확인된 것과 아직 확인되지 않은 것

| 구분 | 상태 |
| --- | --- |
| 과거 코드의 요청 ID 충돌 가능성 | 발견되어 예방 수정 |
| 조기 완료 판정 가능성 | 발견되어 예방 수정 |
| 캐러셀 부분 저장 처리의 취약점 | 발견되어 보완 |
| 오프라인 회귀 테스트 | 2026-10-19 작업 시점 53개 통과 확인 |
| 기존 1,178건 전체의 손상 여부 | **미확인 — 로컬 DB 진단 필요** |
| 기존 계정별 1년치 연속 커버리지 | **미확인** |
| 수정된 코드의 Windows 실수집 안정성 | **미검증** |
| 최종 운영 승인 | **미승인** |

코드 수정이나 CI 통과만으로 기존 데이터가 정상이라고 단정하지 않는다.

## 4. 재발 방지 원칙

1. **데이터 계약 선행:** 계정·게시물·미디어·관측값·요청·실행·커서의 식별자와 관계를 문서화하고 고정한다.
2. **불변식 우선:** 요청 ID 유일성, 계정 식별 일치, 커서 연속성, 관측 이력 불변성, 트랜잭션 원자성을 자동 테스트한다.
3. **실제 데이터 보존:** 기존 DB와 커서를 삭제하거나 초기화하지 않는다. 수정 전 일관된 SQLite 백업과 원본 JSON 보존이 필수다.
4. **완료 근거 저장:** `backfill_done` 같은 플래그는 검증 가능한 페이지·커서 증거와 함께 기록한다.
5. **불확실성 명시:** 확인 불가능한 상태는 `UNKNOWN`으로 표시한다. 추측을 `PASS`로 올리지 않는다.
6. **실패 안전성:** 계정 식별 불일치, 인증 실패, 사용량 증거 부재, 로컬 저장 오류, 미해결 배치가 있으면 안전하게 중단한다.
7. **단계적 확장:** 읽기 전용 DB 진단 → 백업 → 오프라인 회귀 → 소량 실수집 → 중단·재개·대조 → 294계정 운영 순으로 승인한다.
8. **검증 책임 일원화:** 여러 AI가 동시에 코드를 바꾸며 설계 불일치를 만들지 않도록 최종 검수 주체와 기준 커밋을 정한다.
9. **최적화 후순위:** 속도·배치 크기·호출량보다 데이터 정합성을 먼저 확보한다.
10. **인수인계 최신화:** 팀원 공유용 MD/PDF는 최종 코드와 실제 DB 검증 결과를 반영한 뒤 배포한다.

## 5. 최종 합격 기준

다음 조건을 충족하기 전에는 '수집 엔진 완성' 또는 '1년치 데이터 완결성 확보'라고 보고하지 않는다.

- 기존 DB의 무결성 검사 결과와 손상·누락 범위가 문서화되어 있다.
- 계정별 요청·게시물·관측값·미디어·수집 상태가 대조 가능하다.
- 실제 API 수집 후 중단·재개해도 중복·누락·커서 역행이 발생하지 않음이 확인된다.
- 과거 1년 완료는 페이지 연속성과 종료 근거로 증명한다.
- 실패 계정, API 제한, 부분 캐러셀, 미확인 구간이 별도로 표시된다.
- 로컬 환경에서 제한적 실수집을 통과하고 운영자가 수집 확대를 승인한다.
