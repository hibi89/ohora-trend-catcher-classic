# OHORA Trend Catcher — 장기 RAW 수집·데이터 자산·4탭 대시보드 목표

- 논의 일시: 2026-10-18 KST
- 프로젝트: `hibi89/ohora-trend-catcher` / 프로젝트 등록부 `hibi89/project-book/BOOK.md`의 p6
- **문서 지위: 사용자와 논의한 목표 및 권장 설계의 기록. 개발·실 API 수집·스케줄러 실행 승인 문서가 아니다.**
- 기존 코드, 기존 로컬 원본, 사용 중인 DB·토큰을 변경하지 않는다. 이 문서를 기록하는 행위 자체로 실제 수집 범위, 시간표, API 호출 비용에 대한 추가 승인이 생기지 않는다.

## 1. 사용자 목표(방향성 확인, 세부사항 토론 중)

**현재 공식 입력 목록 294계정(KR 100 / US 101 / JP 93)의 최근 게시물부터 계정당 50개를 쌓는 것이 첫 번째 데이터 확보 목표다.** 모두 조회 가능할 때 총 14,700개 게시물이며, API 접근/삭제/게시물 수/한도/호출 성능에 따라 실제 수량은 낮을 수 있다. 캐러셀 하위 이미지·영상은 게시물 개수와 별개로 관리한다.

50개는 종료 상한이 아니라 **초기 확보 기준**이다. 이후:
1. 각 계정의 새 게시물이 올라오면 계속 추가한다(최신 동기화).
2. 동시에 기존에 확보한 가장 오래된 게시물의 이전 페이지를 찾아 누적한다(과거 백필).
3. 데이터 기간을 우선 과거 1년, 가능하면 과거 2년까지 확장한다.
4. 장기적으로 트렌드 비교가 가능한 원본 자산을 구축한다.

'50개'와 '1년/2년'은 다른 성공 기준이다. 계정별 게시 빈도가 달라 50개가 커버하는 기간은 제각각이다. **과거 1·2년 전체를 무결하게 확보했다고 주장하려면 연속 페이지/오류/삭제·권한 제한까지 검증해야 한다.**

**지금은 수집 시스템의 설계 기준을 만드는 참고 구상이다. 탭의 화면·점수 공식·AI 모델·완료 일정은 아직 확정하지 않았다.**

## 3. 권장 수집 엔진: 세 가지 독립 작업

### A. 최신 동기화(front refresh)
- 계정별 최근 페이지부터 조회하고, 이미 저장한 최신 게시물 ID와 겹치는 지점을 확인해 신규 게시물만 더한다.
- 신규 게시물이 한 번의 페이지 크기보다 많을 수 있으므로 단순히 매번 '최신 5개'만 요청해서 최신 동기화 완료로 판정하지 않는다.
- 확인한 시점·조회 범위·새로 발견한 ID·페이지 완료/중단을 남긴다.

### B. 과거 이력 확장(backfill)
- 계정별 가장 오래된 확보 게시물과 페이지 커서를 관리해 더 과거로 확장한다.
- 계정당 50개 확보 후에는 수집을 영구 중단하지 않고 **과거 1년, 가능하다면 2년의 날짜 목표**로 전환한다.
- 기존 `experiments/rolling_backfill.py`는 5개 단위 커서와 `TARGET=50`을 전제로 설계되어 있다. 최신 동기화와 기간 기반 계속 확장은 **아직 구현된 기능이 아니다**.
- Business Discovery 커서가 버전·인증 범위에서 실제 동작하는지 소수 계정 실측이 필요하다.

### C. 지표 재관측(metric observations)
- 게시물의 좋아요·댓글 수와 계정 팔로워 수는 시간에 따라 변한다. 후속 수집 시 **관측 시각이 붙은 별도 기록**으로 남기는 설계를 권장한다.
- 과거 게시물에 대해 현재 얻은 좋아요 수를 '게시 당시 좋아요 수'라고 주장하지 않는다.
- API 예산을 고려해 모든 오래된 게시물을 같은 빈도로 다시 조회할 필요는 없다. 구체적인 재관측 우선순위/주기는 추후 협의한다.

### 호출 우선순위(제안, 확정 아님)
1. 최신 게시물 누락 방지
2. 50개 미만 계정 초기 채우기
3. 50개 채운 계정의 1년→2년 과거 확장
4. 기존 지표의 추가 관측

할당은 API 한도·실제 시간·대시보드 중요도에 따라 조정한다. **여러 Meta 앱이 있다고 자동으로 한도가 독립이거나 2배가 되는 것은 아니다.** 기존 150/144 구획 및 90분/70% 설정은 검증된 성능 수치가 아니라 기존 코드의 현재 설계/안전장치다. 현재 마지막 기록상 두 번째 앱의 과거 인증정보는 만료 상태이며 2앱 실운영 미검증이다.

## 4. 저장·조회 분리와 권장 논리적 데이터 구조

**핵심 원칙: 실행별 RAW 응답 보존 + 장기 누적 식별자 기준 DB + 대시보드 읽기 전용 계층 + 파생/AI 분석 별도 계층.**

- 공식 `input_accounts`: 입력 계정명/계정 키/국가를 수정 없이 보관. API가 응답한 `username`과 입력 `input_username`을 구별.
- `accounts`, `posts`, `post_media`: 원본 식별자 관계 및 게시물/캐러셀 구성.
- `account_observations`, `post_observations`: 팔로워·좋아요·댓글 등 반복 관측값을 `observed_at`과 함께 보존.
- `collection_state`: 계정별 최신 동기화 진행 위치, 과거 커서/가장 오래된 게시일, 50개·1년·2년 커버리지 및 중단 상태.
- `collection_log`, `field_support`, `run_manifest`: 배치 외부/내부 응답 구분, 오류·미지원 필드, 완료/부분/실패, 실제 계정·게시물·미디어 수, 결과 해시, 버전.
- `raw_responses`: 실행별 받은 API JSON 파일 경로/해시/요청 식별자; 비밀값과 paging URL의 토큰을 마스킹.
- `design_classifications`, `trend_scores` 등은 **RAW에 만들지 않고** 별도 분석 영역에서 파생·버전 관리한다.

매 실행 `data/<run_id>/` 안에 그 실행의 원본 응답 JSON/CSV/manifest를 남기는 방향을 따른다. 지속 누적 DB는 실행 폴더 교체와 무관한 별도 위치에서 재개 가능해야 한다. 기존 실험 데이터/로컬 DB를 새 본 수집에 자동 병합하거나 덮어쓰지 않는다. 기존 코드의 계정별 delete-and-replace는 신규 장기 관측 보존 요구와 상충하므로 **신규 RAW 계층을 별도 구현하고 검증된 Meta API 요청 코드를 선택적으로 재사용**하는 것이 현재 권장안이다.

**RAW 보존 규칙:** `caption`·`biography` 원문·시각·문자열형 ID·미반환과 실제 0의 구분·관측 시점·캐러셀 자식 목록/순서 보존. 임의 번역·해시태그 추출·참여율 계산·트렌드 점수·AI 분류는 RAW에 추가하지 않는다. 이미지 URL과 실제 이미지 파일 확보를 구별한다. `ig_id`/`id`/`ig_user_id` 및 선택 필드 `shortcode`/`view_count`는 실제 Meta 경로에서 별도 검증한다.

### 저장 기술 선택(권장, 미확정)
- 초기 단계: SQLite + 실행별 JSON/CSV로 낮은 비용과 로컬 복구성 확보.
- 원격/다중 사용자 동시 조회가 실질적으로 필요해질 때 서버형 DB를 재평가.
- 앱 UI F5/대시보드 조회 또는 AI 질문은 수집·유료 비전 분석을 트리거하지 않는다. 조회는 저장된 DB/캐시를 읽는 경로로 분리한다.

| P6 | 4탭 조회·트렌드/AI 분석 연결 | 실제 DB 기반 조회·정렬·가중치·AI 근거·관제 검증 |

P2가 완전히 끝나기 전이라도 **개별 계정이 50개를 채우면 최신 유지 및 과거 확장을 병행할 수 있게 설계**한다. 데이터 없는 계정을 결과에서 숨기지 않는다. 1년/2년이 API와 계정 게시량상 가능하다는 보장은 없다.

## 6. 주요 위험과 미확정 사항

- 과거 1~2년 조회 가능 범위/커서 지속성/미디어 children 다음 페이지: **실 API 미검증**.
- 원본 이미지 URL 만료·접근 제한·실제 파일 다운로드 정책: **별도 승인 필요**. URL 확보가 원본 파일 저장을 뜻하지 않음.
- 계정별 신규 게시물 누락 탐지와 삭제/비공개/기존 누락 구분: 구현·검증 필요.
- Meta 앱별 호출 사용량, 속도, 호출 간격, 주기적 예약, 토큰·권한과 운영 환경: 실측/승인 전제. 5분 완주 또는 90분 회복 보장 불가.
- 트렌드 가중치 공식·계정 보정·국가별 편향/수집 커버리지 표기: 팀과 추가 협의.
- AI 챗의 쿼리 권한·검증/비용 통제·표/그래프 생성 범위: 팀과 추가 협의.
- 목표 50개, 1년, 2년은 **희망하는 범위**이지 수집 성공/확보 완료 선언이 아님.
