## 2. 작업 우선순위 (효용/의존성 순서)

### P0 — 현재 상태 보존과 팀 납품 (우선)

**T01. 현재 운영 스냅샷/증거 보존 (오프라인)**
- 해야 할 일: SQLite `backup.py`로 새 일관 스냅샷; 별도로 `runs` 원본 JSON·CSV·manifest 사본; `audit.py`, 마지막 `verify.py`, 백업 SHA/날짜/DB 수치를 인수 기록에 고정.
- 완료 기준: **동일 snapshot에 대해** 294/286/8, 1,330고유, 1,350 관측 및 audit PASS 재확인. DB snapshot만으로는 원본 JSON 보존 부족.
- 중단 기준: 해시 불일치, 누락된 raw, 미해결 batch, audit FAIL. 이 경우 납품 보류 및 [SOP](RAW_V2_ERROR_HANDLING_RUNBOOK.md) 이행.
- 담당: 수집 담당 + 전달 전 팀 검수. **미실행:** 이 문서만 GitHub에 올리는 것으로 로컬 백업이 새로 만들어지지는 않음.

**T02. 팀 전달용 데이터 패키지와 계약**
- 산출 후보: 계정 상태/메타정보, 고유 게시물, 미디어/캐러셀, 게시물별 관측값, 필드지원·좋아요 누락 진단, 실행 단위 감사 요약; 팀의 실제 분석 컬럼 요구에 맞춰 CSV/JSON을 선택.
- 처리: timestamp UTC와 분석용 KST 구분, 계정 키를 국가별 공식 키와 일치, 게시물 ID 문자열 무손실, `0` vs `NULL` vs `absent`, 고유 post와 관측 레코드의 cardinality 구분, Instagram 프로필/게시물 URL 정규화·검증.
- 보호: 토큰·인증파일·raw Meta trace·민감 개인정보 없는지 스캔, 공개 저장소 아닌 승인된 전달 경로 사용. Meta 플랫폼 사용약관과 데이터 공유 권한을 팀에서 확인.
- 완료 기준: **팀원이 새 환경에서 파일을 읽어** 국가별/계정별 count와 샘플 기록 대조, 파일별 SHA256·스키마/누락값 정의 제공, 실패 8개 별도 표기, 데이터 시점과 API-visible 한계 기재.
- 주의: 현재 이 항목의 최종 통합 배포 ZIP/계약 검증은 **완료 보고가 없으므로 미완료**.

**T03. 간단한 전달용 결과 요약·재현 지침**
- 필수: 294/286/8/1330/1350, 감사 0/0/0, History 10계정에서 신규 40, 마지막 run ID, 8개 키 목록, 좋아요 필드 공백 이슈, 사용자명 변경/Meta 접근 한계, 무인 미승인, 실행·검증 명령, 장애시 SOP 링크.

### P1 — 정확도/오류 통제 강화 (후속)

**T04. 8개 Meta 110 오류 세분화 (API 추가 호출 전 오프라인)**
- JP_093은 이미 원본 `110/2207013`, `is_transient=false`, 브라우저 페이지 접근 불가 관측 완료.
- **나머지 7개**는 각자의 raw에서 `error_subcode`, `is_transient`, `error_user_msg`, 응답 시각, 해당 계정 키를 추출. 계정 존재/변경/권한 문제를 **증거 수준별** `CONFIRMED / LIKELY / UNKNOWN`으로 라벨링.
- 완료 기준: 8개 전부 원본 경로+응답 시각+메시지+확인 상태 표; **계정 삭제 판정은 별도 근거 없으면 하지 않음**. 공식 원본 수정·blocked 강제해제 없이 수행.

**T05. 단일 계정 격리 재조회 기능 (현재 없음 → 별도 설계/구현/회귀 검증 필요)**
- 목적: 계정명이 수정됐거나 권한이 복구된 **한 계정만** 재조회하여 수정 여부 입증.
- 요구: 공식 294키/원본 해시 불변; account_key whitelist 1개와 phase/front 제한; 구차단 상태 보존한 진단 모드 또는 승인된 상태 전이; dry-run에서 **실제 대상·요청·커서·쿨타임** 검증; 요청 1회 한도; 원본 JSON/응답·감사·메타 쿼터 기록; 동시 실행 잠금; 재요청 사유와 사용자 승인 이력.
- 테스트: 기존 8개 차단 그대로인 경우 안전하게 거절; whitelist 외 요청 0; 성공/110/권한 오류/타임아웃/응답 저장 실패/재실행/슬롯 한도/후속 front 단계 케이스 모의.
- 완료 기준: 로컬 합성 회귀 PASS + 백업 + 실제 사용자가 **1계정 1회 승인**할 때만 실험. 현재 `--target-legacy-ten`은 **고정 10 History 전용**이고 개별 110 계정을 되살리는 기능이 아님.

**T06. 지정 10계정 History 특수 경로의 테스트·정리**
- 실제 10계정 ×4 HTTP 200은 사용자 로그로 입증. 그러나 옵션 `--target-legacy-ten`의 별도 테스트 추가와, 기존 대상 10개가 증거 연결을 마친 지금 계속 사용해야 하는지 검토.
- 테스트: 요청 10개 정확히 한 번씩·2배치, 이미 처리한 계정의 재요청 방지, pending front/catchup에서 안전 거부, 사용량 임계값, 예외·부분 실패·KST 날짜 경계, `--live` 없는 DB 미수정. **실사용 성공만으로 모든 실패 경로가 검증되지는 않음**.
- 완료 기준: 신규 테스트와 전체 93개 회귀 PASS, 변경 전후 동일 로컬 DB에서 read-only audit 0/0/0, 기존 수집 기록 불변. **핫픽스는 필요한 오류가 발견됐을 때만**.

**T07. 진짜 History 커버리지 판정**
- 대상별 목표: **실제 365일(장기 730일)** 범위·첫 root·모든 after cursor·페이지 순서·타임스탬프·종료/고정 cutoff 근거, 누락 catchup/가려진 컨텐츠/접근 제한의 경계를 구분.

- 완료 기준: “**무결한 기록 체인**”, “**Meta API에 보이는 365일 구간 확인**”, “**인스타그램 전체 컨텐츠 완전성**”을 서로 다른 상태로 보고. 불가능한 항목은 UNKNOWN으로 유지. 무조건 294/294나 전량 완료라고 하지 않음.
- 실호출 필요 시: front 우선·쿨타임·85% 사용량·배치 5·슬롯 150 유지, 사용자 승인.

## 5. 마지막 판정 문구

> **2026-10-19 현재 사용자 로컬 RAW v2.1은 실측된 감사 항목에서 PASS이며 오류 10건의 역사적 증거 경고는 해소되었다. 하지만 차단 8계정, 실제 기간 완전성, 팀 인수 ZIP, 무인 자동수집 승인 및 운영 검증은 각각 별도 미완료 과제다.**

이 문구보다 강한 완료 표현을 사용하려면 해당 항목의 **최신 사용자 로그/검증된 파일과 acceptance 근거**가 필요하다.
